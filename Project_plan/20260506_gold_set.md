# Phase 1 Gold Set — Template

**Date:** 2026-05-06
**Purpose:** Template + reference for authoring the 10-question Phase 1 gold set. The eventual `eval/gold_set.csv` is filled in using this format. This file documents the *distribution rationale*, the *field data dictionary*, and one *worked example* (Q01) showing how a row should look.
**Companion docs:** [Project_plan/20260506_project_plan_evaluation.md](Project_plan/20260506_project_plan_evaluation.md) §2 — explains why this gold set exists and how each field drives a metric.

## 1. Abstract — distribution of the 10 questions

The 10 questions split across four categories:

| Category | # | % |
|---|---:|---:|
| Cross-source synthesis | **5** | 50% |
| GDOT-only treatment lookup | 2 | 20% |
| Road-data lookup (roadSegments OR locations) | 2 | 20% |
| Refusal (deliberately out-of-corpus) | 1 | 10% |
| **Total** | **10** | 100% |

Paraphrases for consistency testing are **not** counted as separate questions — they're added as `paraphrase_1` / `paraphrase_2` columns on 1–2 of the cross-source rows.

### 1.1 Why cross-source is weighted at 50%

Cross-source synthesis is PavePal's killer use case: *"this street is at PCI 80 with these defects — what does the GDOT guide say to do?"*. A single question that requires retrieving from BOTH the road-data JSONs AND the GDOT PDF, then synthesizing the two with the LLM.

Three reasons cross-source gets half the gold set:

| Reason | Detail |
|---|---|
| **It's the use case** | The whole reason we have hybrid retrieval + JSON flattening + source-aware policy B is to enable cross-source answers. Without weighting it heavily, our headline metric measures something other than what we're actually building. |
| **It's the hardest test** | Cross-source exercises every link in the chain: dense retrieval, sparse retrieval, RRF fusion, source-aware filtering, AND LLM synthesis. If cross-source recall is high, single-source is almost certainly higher. The reverse isn't true. |
| **It's the only test that proves source-aware retrieval works** | Per-source recall@5 (the new metric in eval plan §3.2) only fires when the gold answer spans multiple sources. Cross-source rows are where that metric earns its keep. |

### 1.2 Why GDOT-only and road-data each get 20%

These are **isolation tests**. If cross-source fails on Q05, we need to know whether the failure is in retrieval (one source didn't get hit) or generation (both sources retrieved but the LLM didn't synthesize). The single-source categories diagnose that:

| Failure pattern | Diagnosis |
|---|---|
| Cross-source fails AND GDOT-only fails | GDOT retrieval channel is broken (regardless of synthesis) |
| Cross-source fails AND GDOT-only passes | Synthesis layer is the problem — retrieval works in isolation but not when fused |
| Cross-source fails AND road-data fails | Same logic, road-data side |

2 questions per category is the minimum to spot a *pattern* vs. a single anecdote. With 1, you can't tell whether a fail is a fluke or a real signal.

### 1.3 Why refusal is only 1 question

Refusal calibration tests whether the system says "I don't have that information" instead of confabulating when asked something out-of-corpus. Important behavior, but at n=1 the metric is **binary per run** (refused or not) — anecdotal, not statistical.

We track it because catching one obvious confabulation is still useful. We don't claim it as a defense pillar in the capstone report. (Eval plan §5.1 documents this caveat.)

### 1.4 Why 10 questions total, not 30

Industry default for a RAG gold set is 30+ questions. We're constrained to 10 due to partner availability for authoring (the partner has to provide the ground-truth answers — we can't fabricate them). Eval plan §2.4 lays out the consequences:

| Consequence | Mitigation |
|---|---|
| Single-question variance shifts metrics by 0.10 | Read trend direction across runs, not absolute thresholds |
| Per-category aggregates are thin (5/2/2/1) | Per-question deep-dive replaces category aggregates |
| Refusal is a binary anecdote | Track but don't headline |

Not fatal — just honest about what the numbers can and can't say.

## 2. Field data dictionary

Each row in the gold set has 9 fields, grouped by role.

### 2.1 Identity fields — track which question is which

| Field | Type | Required | What it is |
|---|---|---|---|
| `qid` | string | ✅ | Unique question ID like `Q01`, `Q02`. Stable across runs — used to compare the same question's metrics over time. No semantic content. |
| `category` | enum | ✅ | Exactly one of: `cross_source`, `gdot_only`, `road_data`, `refusal`. Drives per-category metric breakdowns. |

### 2.2 Input fields — what gets fed to the RAG system

| Field | Type | Required | What it is |
|---|---|---|---|
| `question` | string | ✅ | The primary user query the system receives. Should sound like something a real PavePal user would actually type. |
| `paraphrase_1` | string | optional | Same underlying question, reworded. Filled in only for the 1–2 cross-source questions used in consistency testing. Tests whether the system gives the same answer when the wording changes. |
| `paraphrase_2` | string | optional | A second rewording. Same purpose as `paraphrase_1`. Three forms total (original + 2 paraphrases) gives a more robust consistency signal. |

### 2.3 Answer-key fields — what the system's output is compared against

| Field | Type | Required | What it is |
|---|---|---|---|
| `gold_chunks` | list of strings | ✅ (empty for refusal) | The chunk IDs that contain the correct answer. The system's top-5 retrieved chunks are checked against this list to compute Recall@5, Precision@5, MRR, and Hit Rate@5. |
| `expected_sources` | list of strings | ✅ (empty for refusal) | Which sources the answer should come from. Subset of `["GDOT", "roadSegments", "locations"]`. Drives per-source recall@5 — the metric that proves source-aware retrieval (policy B) is working. |
| `canonical_claims` | list of strings | ✅ | Short factual phrases the answer text should contain. Used for substring matching in consistency testing (method #2) and claim coverage scoring. Choose **lowercased substrings** that catch reasonable variants (e.g., `"preventive"` matches "preventive maintenance" and "preventive treatment"). |
| `reference_answer` | string | ✅ | The full gold-standard answer in prose. Used by the LLM-as-judge to score the system's answer for correctness and groundedness. Should be concise — 2–4 sentences — and cite the right source. |

### 2.4 Data flow — which field drives which metric

```
gold_chunks      ─────►  Recall@5, Precision@5, MRR, Hit Rate@5  (retrieval, §3.1)
expected_sources ─────►  Recall@5 by source                       (per-source, §3.2)
canonical_claims ─────►  consistency_score #2, claim coverage     (consistency, §4.2)
reference_answer ─────►  LLM-judge correctness + groundedness     (hallucination, §4.1)
paraphrase_1, _2 ─────►  consistency_score #2, #3, #4             (consistency, §4.2)
```

Section references are to [Project_plan/20260506_project_plan_evaluation.md](Project_plan/20260506_project_plan_evaluation.md).

### 2.5 Special case — refusal questions

Refusal-category questions test whether the system declines to answer when the topic is out-of-corpus.

| Field | Refusal-row value |
|---|---|
| `category` | `refusal` |
| `question` | A question the corpus does not cover (e.g., *"What does GDOT say about railway crossings?"*) |
| `gold_chunks` | `[]` (empty — there are no relevant chunks) |
| `expected_sources` | `[]` (empty — no source should hit) |
| `canonical_claims` | A refusal phrase like `["i don't have", "not in the"]` |
| `reference_answer` | A short refusal: *"This question is outside the scope of the GDOT guide and the road data we have."* |

## 3. Example — Q01 (cross-source synthesis)

### 3.1 Filled-in row

> **Note on GDOT's selection framework.** GDOT keys **treatment selection** off distress type + severity level + traffic ADT (see **Table 66, p. 390**), not directly off PCI. PCI is used separately for **timing decisions** (Figure 1, p. 9 — preserve early in life when condition is still high) and for **effectiveness research** (Conclusions, p. 3 — crack sealing is 52–72% effective on pavements in the COPACES 79–85 range). The reference answer below reflects that two-pronged framework. The PACES manual (GDOT Appendix B) defines severity levels.

| Field | Value |
|---|---|
| `qid` | `Q01` |
| `category` | `cross_source` |
| `question` | "What treatment does GDOT recommend for Peachtree Industrial Blvd Access Rd?" |
| `paraphrase_1` | "Per the GDOT guide, what's the appropriate maintenance for Peachtree Industrial Blvd Access Rd?" |
| `paraphrase_2` | "What pavement preservation activity should we apply to Peachtree Industrial Blvd Access Rd?" |
| `gold_chunks` | `["roadSeg_<peachtree_id>", "GDOT_p390", "GDOT_p003"]` *(placeholder IDs — page 390 = Table 66 selection guidelines; page 3 = COPACES effectiveness research.)* |
| `expected_sources` | `["roadSegments", "GDOT"]` |
| `canonical_claims` | `["transverse", "longitudinal", "crack seal", "severity"]` |
| `reference_answer` | "Peachtree Industrial Blvd Access Rd has a PCI of 82 with 5 transverse cracks and 12 longitudinal cracks per the road-segment data. GDOT's AC Pavement Treatment Selection Guidelines (Table 66, p. 390) key treatment selection off distress type, severity, and traffic — not directly off PCI. The transverse cracks fall under GDOT's Block/Transverse Cracking category; the longitudinal cracks map to either Load Cracking (if in wheelpaths) or Reflection Cracking. GDOT's effectiveness analysis (p. 3) shows crack sealing is 52–72% effective on pavements in the COPACES 79–85 range — which includes PCI 82 — and GDOT's updated criteria allow crack sealing up to a maximum COPACES of 85–90. Crack sealing is therefore the recommended treatment here for low-severity (Level 1) cracks; higher severities reduce effectiveness and may warrant chip seal or thin overlay. The road-segment data does not include severity levels, so a PACES-manual assessment (GDOT Appendix B) would be needed to finalize." |

### 3.2 Key choices made

| Field | Choice | Reason |
|---|---|---|
| `question` | Used a real road from `roadSegments` | Peachtree Industrial Blvd Access Rd is record 1 in the actual JSON (verified in research log §Running examples). PCI=82, defects = 5 transverse + 12 longitudinal cracks. Real, checkable ground truth. |
| `question` phrasing | Did NOT include "PCI 82" in the question | If the question included the score, the system could skip the roadSegments retrieval entirely. Hiding it forces a 2-hop retrieval — which is what makes it cross-source. |
| `paraphrase_2` | Drops the literal word "GDOT" | Tests whether the dense retriever (BGE) can still route to GDOT chunks semantically. If retrieval fails on this paraphrase but works on the original, that signals the BM25 channel is doing all the routing work. |
| `canonical_claims` | Distress-type terms + treatment + severity | Aligns with GDOT's actual selection framework (Table 66 keys off distresses, not PCI bands). `"transverse"` and `"longitudinal"` force the answer to acknowledge the JSON's defect data. `"crack seal"` is the GDOT-recommended treatment per the effectiveness research. `"severity"` forces acknowledgment of the data gap (JSON lacks severity levels). |
| `gold_chunks` | 3 chunks — roadSegments record + 2 GDOT pages | Page 390 (Table 66) is the selection matrix; page 3 (Conclusions) has the COPACES effectiveness numbers. Both are needed for a complete answer. |
| `reference_answer` | Cites Table 66 + COPACES 79–85 effectiveness + max-COPACES-85-90 criterion | All three are verified in the GDOT PDF — Table 66 framework on p. 390, effectiveness data on p. 3. Specific page citations make the LLM-judge's job easier (the judge can verify each claim against the cited page). |

### 3.3 Notes & open questions

A previous version of this section flagged the Q01 reference as "unverified" — based on generic pavement-management knowledge rather than actual GDOT content. Since then we've read the relevant sections of the GDOT PDF and grounded the reference. Residual uncertainties:

| Item | Status | What needs to happen |
|---|---|---|
| `gold_chunks` IDs (`roadSeg_<peachtree_id>`, `GDOT_p390`, `GDOT_p003`) | **Placeholder format** | Real IDs come from inspecting the chunked corpus once Phase 1 indexing runs. The page numbers (390, 3) are verified; the exact chunk-id format will be set by the indexing code. |
| Specific Table 66 cell values for Block/Transverse and Load Cracking rows | **Partially verified** | Structural framework is confirmed (selection by distress + severity + ADT). The table image at p. 390 renders at low resolution, so verifying every cell at the `▶` / `●` / `✗` level would benefit from a high-resolution second pass. |
| Whether longitudinal cracks default to Load Cracking or Reflection Cracking | **Depends on wheelpath location** | The JSON doesn't say where the cracks are. The reference answer hedges this honestly with "Load Cracking (if in wheelpaths) or Reflection Cracking". |
| The JSON's `pci_category="Very Good"` vs GDOT's bands | **Different frameworks** | GDOT (Figure 1, p. 9) uses EXCELLENT / GOOD / FAIR / POOR / VERY POOR / FAILED. The "Very Good" label in the JSON comes from a different (likely city/COPACES-specific) framework. The reference answer avoids the band label and uses the raw PCI score (82) directly. |
| Severity levels not in the JSON | **Real corpus limitation — worth raising with PavePal** | GDOT's selection criteria need severity (Level 1/2/3). The JSON has only defect counts. The reference answer acknowledges this gap and points to the PACES manual for severity assessment. Could PavePal supply severity data? |
